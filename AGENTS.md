# CADPilot — Workspace Guide

## Purpose

MCP (Model Context Protocol) server that lets AI clients (Claude Desktop, LangChain, etc.) control FreeCAD remotely. Two main components communicate over XML-RPC:

1. **MCP server** (`src/cadpilot/`) — Python package run via `uvx cadpilot` or `uv run cadpilot`. Speaks MCP to the AI client and XML-RPC to FreeCAD.
2. **FreeCAD addon** (`addon/CADPilot/`) — Installed into FreeCAD's `Mod/` directory. Hosts the XML-RPC server inside the FreeCAD process and dispatches all document/GUI work onto the main thread.

## Build & Run

```bash
# Install dependencies (requires Python ≥3.12, uv)
uv sync

# Run MCP server locally (developer mode)
uv run cadpilot                          # connects to FreeCAD on localhost:9875
uv run cadpilot --only-text-feedback     # get_view returns a text notice instead of capturing (hard guarantee)
uv run cadpilot --host 192.168.1.100     # connect to remote FreeCAD

# Publish to PyPI (via hatchling)
uv build

# Run tests (MCP server side only; the addon needs a live FreeCAD)
uv run pytest
```

The FreeCAD addon must be installed separately — copy `addon/CADPilot/` into FreeCAD's `Mod/` directory and restart FreeCAD.

## Addon Hot-Reload (No Restart)

During development you can reload the addon **without restarting FreeCAD**:

1. Copy the updated addon files to the live `Mod/` directory:
   ```bash
   cp -rf "H:/My_Software/CADPilot/addon/CADPilot/." \
          "C:/Users/intel/AppData/Roaming/FreeCAD/v1-1/Mod/CADPilot/"
   ```

2. In FreeCAD's Python console (or via `execute_code`) run the one-call restart:
   ```python
   import rpc_server.rpc_server as rs

   print(rs.restart_rpc_server())
   ```
   It stops the server, reloads every loaded `rpc_server.*` module in
   `_RELOAD_ORDER` (dependencies before importers, main module last; a reload
   error is reported in the result and never aborts the restart), then starts
   the server from a deferred self-healing retry loop. The start must be
   deferred because the in-flight XML-RPC request (this call) blocks the old
   server's shutdown drain; attempts run 1 s apart for up to a minute, after
   which the watchdog (`rpc_server/watchdog.py`) keeps retrying every 3 s.

   The watchdog also covers accidents on its own: a start that failed at
   boot, a `serve_forever` thread that died, a port that was briefly stolen.
   It revives the endpoint whenever it is down but wanted. Intent is a
   main-window property, so it survives hot reloads; a toolbar Stop records
   "stay down", while a PROGRAMMATIC stop (this recipe, any execute_code) is
   treated as transient and gets revived within one tick.

3. Wait ~8 seconds before issuing the next MCP call so the new server is ready.

4. If GUI-dispatched calls (e.g. `execute_code`) hang after the reload but
   `ping` still answers, the heartbeat/waker chain died during the race.
   Repair via `execute_code_async` (its worker runs without GUI dispatch):
   ```python
   import rpc_server.gui_dispatch as gd
   from PySide import QtCore
   import FreeCADGui


   def repair():
       while not gd._rpc_request_queue.empty():
           t = gd._rpc_request_queue.get()
           if t is not gd._SHUTDOWN:
               t()
       QtCore.QTimer.singleShot(500, gd.process_gui_tasks)


   QtCore.QTimer.singleShot(0, FreeCADGui.getMainWindow(), repair)
   ```

3b. **Reloading a module does NOT rebind names other modules imported from it.**
   `object_factory`/`feature_ops`/`serialize` do `from .property_mapper import
   set_object_property`, and that binding keeps pointing at the OLD function
   after `importlib.reload(property_mapper)` — the fix silently does not take
   (live: a mapper fix looked live because the module had it, while every MCP
   call still ran the old code). Reload the IMPORTING modules after the
   imported one, or the fix is invisible.

> **Why deferred?** `stop_rpc_server()` calls `shutdown()` which blocks until the current request drains, and `server_close()` must release the socket before `start_rpc_server()` can bind again. Running the restart synchronously inside the same `execute_code` call deadlocks because the request itself is blocking shutdown. The `QTimer` deferral runs on FreeCAD's main GUI thread after the RPC call returns.

## Architecture & Key Constraints

- **GUI thread rule**: All FreeCAD document/GUI operations MUST run on FreeCAD's main (GUI) thread. The addon uses `dispatch_to_gui()` to queue lambdas and a `QTimer` waker to process them. Never call FreeCAD APIs directly from the RPC server thread. User interaction has priority over queued RPC work (`gui_dispatch.py`): on win32 the physical button state (`GetAsyncKeyState`) is authoritative in BOTH directions — Qt's `mouseButtons()` is event-delivered and therefore stale exactly while the event loop is busy, so trusting it alone misses fresh presses and lets tasks start mid-drag (the "frozen while the LLM models" bug); the drain loop also re-checks the mouse/popup/modal guards between tasks so a mid-drain press pauses the backlog, and the phantom caps (static 10s / hold 15s, time-based) exist only for the non-win32 heuristic path — never cap an OS-confirmed real hold. **Early user-interaction report**: a dispatch that arrives while the guard is provably holding the queue waits `_USER_HOLD_GRACE` (2s, `gui_dispatch.py`) and then answers with the actionable reason ("could not act on the document within 2s because the user is holding a mouse button… release it and retry") instead of burning its whole 60s/90s timeout in silence (live complaint: `fillet`/`color` reported "timed out after 60s because the user is holding a mouse button" with nothing said beforehand). 2s is long enough that an ordinary click still completes (the wait polls in grace-sized slices and only gives up once `_defer_reason` is set), the task is cancelled like any timeout, and the old timeout branches stay for a genuinely busy GUI thread or a dead waker. **Modal-blocker recovery without a GUI**: a modal dialog (FreeCAD opens its document-recovery dialog after an unclean shutdown, before any tool can reach the document) holds the whole queue back, so every document call times out while `ping` still answers. Two channels make that recoverable for a client that cannot operate the computer at all (Claude Code, opencode, any MCP client): `gui_dispatch.backpressure()` states WHY the queue is held (mouse button / popup / modal / busy) and is deliberately NOT dispatched, so it answers exactly when nothing else does, exposed as the `get_gui_state` RPC and printed by `diagnose` as a `GUI queue:` line; and `diagnose(dismiss=true)` puts one task on `_force_queue` (addon RPC `dismiss_blocking_dialog`), which skips the guards, and closes the active modal with `widget.reject()` (Cancel semantics, so nothing is ever confirmed). The dismissal rides on `diagnose` rather than being its own tool (user decision, 2026-10-06): the blocker IS what that report names, the plain `diagnose` must not touch FreeCAD at all because it has to work while FreeCAD is down, and a failed dismissal must still return the report. That is why `diagnose` is annotated as mutating (its `dismiss` option acts) while its default path stays pure, and why the tool list is 27 again. The reason matters because a wedged thread, a mouse drag and a modal all look alike from outside and want opposite advice, and `diagnose` resolves it from the addon rather than guessing: it leads with the tool call and quotes the dialog's own labels in parentheses for a localized UI (文档恢复, 取消/清除/开始恢复) because the prose stays English while the on-screen text does not. The early back-pressure report (the one that fires after `_USER_HOLD_GRACE` for any of the three guards, instead of burning the whole timeout) also ends with that remedy, so a held-back caller is told what to do next.
- **Two-process model**: The MCP server and FreeCAD run in separate processes. They communicate exclusively via XML-RPC on port 9875. The MCP server never imports FreeCAD.
- **MCP version compatibility**: `server.py` imports `FastMCP` from `mcp.server.fastmcp` (1.x) with a fallback to `MCPServer` from `mcp.server.mcpserver` (2.x). Keep both paths working.
- **Timeouts**: Default XML-RPC transport timeout is 150s. `execute_code` has a 90s GUI-thread timeout; use `execute_code_async` for longer operations.
- **Reconnect**: `FreeCADConnection._invoke` rebuilds the XML-RPC proxy and retries once on dead-connection errors — for READ-ONLY methods only (`_RETRYABLE_METHODS`; anything not listed is treated as mutating). `IncompleteRead`/`RemoteDisconnected`/reset arrive AFTER the request was delivered, and a server that processed the request before the connection died makes a retry a silent second execution, so a mutating RPC raises a RuntimeError telling the caller to inspect the document before repeating it (live-caught by the round-1 stress audit; the fake connection never saw these because they are transport-shaped). Socket timeouts are NOT retried for the same reason. `_invoke_with_screenshot`'s legacy tail-less fallback fires only on DISPATCH-SHAPE TypeErrors (`_DISPATCH_SHAPE_ERRORS`), which provably happen before the handler body runs; an application TypeError that faults after a commit used to hit the same fallback and re-run the mutation without its `doc_name` binding.
- **Screenshot handling**: `get_view` is the ONLY screenshot tool; every other tool is text-only (no `with_screenshot` params anywhere). Delivery is file-only (`screenshot_store.py`/`responses.py`): the PNG is written to `$CADPILOT_HOME/screenshots/` (keep last 100) and only the file path is returned, so image data never enters the context (a multimodal client reads the file with its own file tool); a failed save degrades to a text notice. `--only-text-feedback` is a hard off: `get_view` then returns a text notice instead of capturing (`ServerState.only_text_feedback`). When no explicit size is given, the long edge is capped at 384px (`DEFAULT_MAX_DIM` in `view_manager.py`). **Capture failures name their cause**: `get_active_screenshot` returns base64-or-`None` on the wire (an error dict would be fed to an old server's base64 decoder), so the reason rides out of band in `rpc_server._last_screenshot_error`, exposed by the `get_last_screenshot_error` RPC and read by `get_view_operation` — every failure path records one (unresolvable view, a view type without `saveImage` such as TechDraw/Spreadsheet, the `save_active_screenshot` error string, a GUI-dispatch timeout, an unreadable PNG). The old single message blamed the view type for all of them, which sent callers hunting a workbench when the real cause was an occluded/minimized window or a stale frame; the failure text now suggests `focus_object=<name>`, which genuinely rescues those because the focus path skips `fitAll()` and forces a repaint before `saveImage` (`view_manager.py:141-167`). The client proxy (`FreeCADConnection._invoke_with_screenshot`, the `screenshot=` kwargs) and the addon's mutation-attached capture (`_run_op_with_screenshot`) still exist for OLD PyPI MCP servers that send a screenshot spec; the current operations never send one.
- **Async tasks**: `execute_code_async` returns a `task_id`; status, `task_print()` output, and tracebacks are kept in a bounded in-memory registry (`_async_tasks`, FIFO max 50) and polled via `get_task_result`. `sys.stdout` is never redirected for background tasks (process-wide race).
- **Unified cad() tool**: All mutations go through `cad(operation=...)` (nsforge math()-style dispatcher) to keep the tool list small. Steps: the operation functions in `operations/core.py` remain the implementation; `cad_operation` dispatches and records session steps. Scope is modeling-only — FEM analysis, the parts library, and `reload_document` were removed in v0.2. Feature ops (boolean/fillet/chamfer/loft/sweep/mirror/pattern, plus Sketcher/PartDesign: variables/sketch/pad/pocket/revolution/groove/thickness/draft since v0.3, plus datum_plane/hull since v0.4, plus the geometry-free `move` and `color`) share the single RPC `create_feature` and pass params as a spec dict (obj_name = base, obj_properties = params). For `sketch`/`variables`/`datum_plane`/`hull`, obj_name names the NEW object and `spec["base"]` carries it (see `CAD_NO_BASE_OPERATIONS`). Sketches are built atomically in `sketcher_ops.py` (geometry + constraints in one transaction, solver runs immediately); results carry `dof`/`fully_constrained`/`warnings` via `describe_feature`, failures roll back with solver diagnostics. Thickness/draft support both the FreeCAD ≥1.1 LinkSub `Base` layout and the ≤1.0 `Faces` property (probe `PropertiesList`).
- **Sketch mode details** (live-verified on FreeCAD 1.1.3): sketch `external: [[obj, "EdgeN"|"VertexN"], ...]` adds external geometry (GeoIds from -3 in list order, start/end points ONLY — `mid`/`center` on external ids fails at solve with MalformedConstraints, so `_check_external_point_refs` rejects it up front); out-of-body targets are auto-bridged via `PartDesign::SubShapeBinder` (`_external_binder`, idempotent `Ext_<obj>_<elem>`) because PartDesign rejects external geometry outside the sketch's body, and `addExternal` takes `(str, str)`. **Base planes are FreeCAD's origin planes** (`_BASE_PLANES` holds their yaw/pitch/roll: XY (0,0,0), XZ (0,0,90), YZ (90,0,90)) — `plane="XZ"` and `datum_plane("XZ")`+`plane={"datum": …}` must mean the SAME frame, or one profile comes out mirrored: the table used to hold R_x(-90) for XZ, so a profile's +v went to global −Z and the solid landed below the XY plane while the datum path put it above (live: a mug revolved to z −90..0 instead of 0..90). A base-plane sketch echoes `plane: {plane, offset, x_axis, y_axis, normal}` in global terms, because "which way is +v" is the single most surprising thing about a non-XY plane. `datum_plane` attaches a PartDesign::Plane to an origin plane (`body.Origin.OriginFeatures` Role lookup) or an existing face (FlatFace + optional offset); sketches attach via `plane={"datum": name}`. `hull` = visual hull: intersect 2-3 view-profile sketches extruded along their sketch normals (extent = union bbox projected per-normal ±`margin`, default max(1mm, 5% of diagonal)); result is a STATIC `Part::Feature` (no proxy — survives document reload), same-name re-run replaces the Shape in place (iterate), multiple solids → largest wins, empty intersection → RuntimeError. v1 limits: view sketches at the global origin, one closed outer profile per view. **Attachment fusion**: pad/pocket on a sketch attached to a solid's face (directly or through a datum plane) operate on THAT solid via attachment — pocket cuts it, pad fuses into it; do NOT pad-then-boolean-cut (the pad already contains the base solid). **execute_code + openTransaction**: the RPC handler now opens a transaction around every snippet and aborts it if the code raises, so a failing run rolls back cleanly and a leaked transaction can no longer poison later recomputes — user code that prefers to manage its own transaction still works (they merge; see the transactional-`execute_code` bullet).
- **Coordinate frames for Body members (v0.5.16)**: a PartDesign feature's `.Shape` is in its BODY's frame with the sketch's plane attachment already baked in, so `global_placement(member)` is **the owning Body's `getGlobalPlacement()`** — never the member's own, which multiplies the same rotation in twice (live: an XZ pad read y −20..0 / z −5..0 for a Body at the origin, `check_interference(Pad, Body)` reported a 4000 mm³ self-overlap as "no intersection", and Part.getShape agreed with `.Shape`). The BODY itself is the other way round: `Body.Shape` is body-local and `body.getGlobalPlacement()` maps it.
- **Geometry sensing**: `measure_geometry`/`get_topology`/`check_interference` are read-only Shape queries (addon `geometry_query.py`), dispatched to the GUI thread without a transaction. Values carry 6 significant digits (`_r`; 4 made a caller's delta the same order as the operands' rounding — a 0.05 mm wall change on a 240 mm part) and `bbox` is OCC's `BoundBox` (exact for planar shapes, ±~0.1 mm on curved ones — `optimalBoundingBox` is not tighter, it is padded by its own tolerance); topology lists are size-sorted and paginated (`limit`/`offset`).
- **Assembly toolchain**: `get_anchors`/`set_anchors`/`assemble`/`verify_assembly` (addon `assembly_ops.py`) give the model data-driven spatial awareness — no screenshots required. Anchors are named points+directions: auto-derived per object (`bbox_center/min/max`, `com`, `axis_mid/start/end` from the dominant cylindrical face, `face0-2_center` from the largest planar faces) plus explicit named ones stored as JSON in an `App::PropertyString` named `MCP_Anchors` in LOCAL coords (they follow Placement). `set_anchors(coord_frame="global")` converts via `obj.Placement.inverse()` at write time — use it whenever the source coordinates are global, because many objects carry non-identity Placements. `assemble` takes a mate list `{obj, anchor, target, target_anchor, mode: center|touch|axis, offset}`, applies each mate in one FreeCAD transaction, then RE-RESOLVES the anchor post-move to report per-mate residuals (mm + deg) and aborts on `tolerance` violation; partial commit via `commit_if` when at least one mate passed. `verify_assembly` audits the whole document: floating objects (nearest-neighbour distance via bbox prefilter + `distToShape`), interferences (common volume for bbox-overlapping pairs), and explicit anchor-pair checks with per-check tolerance. Hidden objects (`ViewObject.Visibility = False` — boolean bases, tool compounds, work geometry) are excluded from the audit and counted in `summary.skipped_hidden`; PartDesign features are excluded as `skipped_body_members` (a member is not a separate solid — `Body.Shape` IS its tip's result, so auditing both reported the feature overlapping its own body as a 6283 mm³ "interference"). `_auditable_shape` rejects shapes OCC cannot measure (origin datums are VISIBLE with an INFINITE bound box, an empty sketch has no faces): feeding either to `distToShape`/`common` threw straight out and killed the whole audit on every default PartDesign document — silently, because the auto-audit swallows exceptions — so an unmeasurable pair is now counted in `summary.skipped_unmeasurable` instead of aborting the scan. The audit's cheap bbox prefilters use `_audit_bbox` (BoundBox `enlarge`d by 0.25 mm) because OCC's box is built from CONTROL POINTS and can under-report a curved shape (a tube-radius-8 torus reports z ±7.94): a prefilter on the raw box skips pairs that really touch (a false island) and inflates nearest distances into false "floating" reports — the exact `distToShape` still decides every pair that survives. PRECISION RULE: `_r()`/`_vec()` rounding (6 sig digits) applies ONLY at the report boundary — `_resolve_anchor`/`_auto_anchor_map` must return RAW `FreeCAD.Vector`s for math (rounding at ~1000mm coords = 0.1mm granularity → false residuals). **Mate ref landings follow FreeCAD's element-type rules** (`UtilsAssembly.findPlacement`): a Vertex lands at that vertex, a circular edge at its CENTER, and the face's own name at the face center — which is why a plain face ref now uses the GUI's `[sub, sub]` marker: the old "nearest vertex" landing mis-placed every CIRCULAR face (its only vertex is the OCC seam) and made a fixed mate of two bolt-hole faces land R−r off axis at residual 0 (live: 44 mm, concentric circles), and a cylindrical ref landed tangent (2.1 mm off a bore axis). A cylindrical ref now lands on the AXIS, so an axle-in-hole `revolute` works, `_axis_ref_notes` names the axis an axis joint will use (the old hard refusal is gone), and `_residual` reports AXIS-to-AXIS distance + axis angle for two rotational faces (`residual_basis: "axis"`) — an axle fit's surface distance is its radial gap, so a 5 mm pin in a 20 mm bore used to read as a 15 mm error. `landing_points` in the mate result gives where each JCS actually landed, and `_landing_warnings` only fires for hint/anchor/point refs (a plain face ref lands on the center by construction). An axis joint aligns the two reference POINTS, so a PARTIAL curved face (its point is the surface's own axis base, not the face center) can slide the part along the axis with residual 0 — live: a hinge revolute translated the lid 20.62 mm along X and buried the barrels (4417 mm³ of interference, `verify` found it, the mate said nothing), so a slide over 2 mm now reports `axial_slide_mm` plus a warning to pin the axial position with `point_on_face`. Assembly `rollback` appends a `verify` summary and WARNS when the document is left disconnected — a placement change the assembly journal never saw (a plain `cad move` on a link) is not restored, and the summary is how that becomes visible. `verify_assembly` also builds a union-find **contact graph** from pairs already scanned (exact `distToShape` ≤ `_CONTACT_TOLERANCE` = 0.5mm, or common volume > threshold) and reports connected components: the largest is the main assembly, the rest are `islands` (with `gap_mm`/`nearest_main`).
- **Connectivity auto-audit**: after every committed `cad()` mutation, `cad_operation` re-runs the read-only `verify_assembly` audit and appends a "⚠ Connectivity" warning (formatted by `_format_connectivity_warning`) to both the tool response and the recorded step's `result_summary`; `detect_risks` surfaces it as a `disconnected_islands` risk in `session(action="status")`. Guards: skipped when `object_count > _AUTO_AUDIT_MAX_OBJECTS` (300), when the addon is old (no `islands` key), or globally via `--no-auto-audit` (`ServerState.auto_audit`). Audit failures never block the mutation.
- **Assembly mode (`assembly_session` tool)**: independent state machine for mate-based assembly with PERSISTENT joints (FreeCAD 1.1 native Assembly workbench — `Assembly::AssemblyObject` with `Type="Assembly"`, `App::Link` components that own Placements, `JointObject.Joint` joints in the JointGroup). Ops: start(ground) / add_component / mate / solve / unmate / rollback(to_step) / verify / status / complete. Mate refs: `{"part", face|anchor|point}` — resolved to `(link, ["FaceN", "VertexM"])` where the vertex sets the mate landing point (GUI click semantics); mate results report `landing` (the actual face/vertex per side) and `warnings` when that vertex sits far from the ref's intent point (face center / anchor position / the point itself — nearest-vertex choice is arbitrary on symmetric faces). `preSolve` (matchJCS) runs before the final single `solve(True)` — skipping it lands mates with faces perpendicular; repeated solve passes corrupt storePrev state. Frames: `link.Shape` is GLOBAL, joint references/`findPlacement` are part-LOCAL; residuals are geometric truth (`fa.distToShape(fb)` + normal angle), never JCS math. `trim={"winner":...}` bakes a non-destructive cut in the loser-link local frame and re-points the link; rollback deletes joints/cuts, re-points links, restores pre-mate placements (precomputed per-step undo, merged by `assembly_state.plan_rollback`). Gap profiles sample the a-face UV grid and measure perpendicular lift from the mate plane (overhang ≠ gap). Every op is journaled with the full spec as params and is replayable from the journal (`EXECUTABLE_OPS` covers `assembly` plus the mate-free `assemble`/`align_shapes`/`set_anchors`); a read-only `verify` commits empty and is downgraded to a non-transactional record by the empty-commit probe, so rollback counting stays exact (live-verified: start→add→mate→verify → `rollback_to 0` = 5 native undos → `replay` rebuilds the mate, residual 0).
- **Global-slot guards (v0.5.16)**: the current session and the current assembly session are each ONE slot per MCP server process, and several agents share a process (subagents of one client!) — so `session(action=status/get_steps/rollback/redo/…)` and every `assembly_session` op except `start` now REFUSE when the passed `doc_name` is not the session's document ("the active session tracks document 'X', not 'Y'"), and `start` reports when it replaces another document's session. Live: an agent's rollback was refused with a stranger session's step range while its own document had 6 valid undo steps, and an assembly rollback aimed at doc A returned doc B's objects (to_step=1 there would have dismantled a stranger's assembly). `doc_name=None` keeps the single-agent flow working.
- **Modeling sessions**: `session_state.py` binds a session to one document. The ten session actions are one MCP tool, `session(action=...)` (start/status/get_steps/rollback/redo/add_note/pause/resume/list/complete); `rollback` requires an explicit `to_step` so a bare call can never wipe the whole session. **Undo-stack ghosts**: FreeCAD 1.1.4 attributes an undo entry to the document that is ACTIVE at commit time, so a transaction committed while another document is active parks a ghost entry (rendered `-> <name>`) on the active document's stack, and undoing there pops the ghost while the real step stays applied (live-verified: a rollback reported N steps undone, truncated its log, and the model never moved). Two-sided fix: every transaction opener runs inside `step_engine.active_document(doc)` (the `_run_op_with_screenshot` task body, `run_record`, `_remove_objects`), and `_stack_op` pops ghosts WITHOUT counting them towards `n` (reported as `ghosts_skipped`) while `_undo_trust` compares the non-ghost sequence. Because ghosts also inflate `UndoCount`, they used to flip the `changed` probe and record a phantom session step. Rollback's `success` now means the model reached the target state (`undone >= n and state_matches is not False`) and `redo` fails loudly when FreeCAD's redo stack restores nothing, instead of answering `restored_steps: []` forever. Every committed mutation runs inside a FreeCAD transaction (addon `_run_op_with_screenshot` wraps `doc.openTransaction`), so session rollback = `doc.undo()` × N + log truncation, where N counts only ATOMIC steps (a non-atomic step provably committed nothing — the addon's empty-commit probe — so it neither blocks the rollback nor consumes a pop; it used to block with a misattributed "execute_code without a transaction" message); removed steps sit in a redo buffer until a new step (mirrors FreeCAD redo semantics), and `restore_steps` drops non-atomic buffer entries as they surface because FreeCAD's redo never re-applied them. `execute_code` is transactional too: the addon wraps the snippet in a transaction and reports `changed` (whether it produced an undo entry), so a mutating run is an ATOMIC session step and rollback undoes it like any cad() call; a read-only run is **not recorded at all** — it owns no transaction, and a step that cannot be undone would break the log's one-transaction-per-step invariant (which rollback's `n = step_count - to_step` relies on); likewise a run that changed a DIFFERENT document than the session's is not recorded — the addon reports `document` alongside `changed`, and recording a foreign-document step would make rollback pop the wrong document's undo stack (direct it to `step_control` on that document instead). Sessions/patterns persist under `$CADPILOT_HOME` (default `~/.cadpilot/`). Mutation results carry an `objects` fingerprint (sorted object names) used to detect state drift after rollback.
- **Transactional `execute_code`**: the RPC handler wraps the snippet in a FreeCAD transaction so its document changes become ONE undo entry — a bare property write is otherwise not undoable at all, which is why an LLM that models exclusively through `execute_code` (very common) produced a journal nothing could roll back. Mechanics (`rpc_server.execute_code`): wrap only when `doc.HasPendingTransaction` is false (transactions do NOT nest — a snippet that opens its own merges into ours, and one that aborts rolls ours back too); an EMPTY commit adds no undo entry, so a read-only run costs nothing; `changed = doc.UndoCount > undo_before` after the commit is the signal (commit/abort return `None`, so the undo count is the only reliable probe); a snippet that raises aborts our transaction, so a failing `execute_code` no longer leaves half-applied mutations. The snippet runs through `rpc_server.exec_snippet`, shared with journal replay so a re-run sees the same namespace. That namespace is this module's globals, so the pre-imported names are exactly `rpc_server.py`'s module-level ones: `FreeCAD`, `FreeCADGui`, `Part` and `App` (`App = FreeCAD`, the alias the GUI console and the docs use). `App.getDocument(name)` RAISES `NameError: Unknown document 'x'` for a name that is not open, it does not return None (live-verified on 1.1.4, hit twice while probing journals): a snippet guard must be try/except or `App.listDocuments()`/`App.openDocument(path)`, and `App.openDocument` on an already-open path returns the SAME document, so it is the safe way to bind to a file that may or may not be open. `Part` and `App` were NOT there while both the tool docstring and `exec_snippet`'s own docstring claimed otherwise (live: a snippet's first line, `Part.makeBox(...)`, raised `NameError`), which is the kind of mismatch a caller cannot debug — anything the docstring promises must be imported at module level, with `# noqa: F401` because ruff cannot see a globals() copy. Live-verified on FreeCAD 1.1.4: mutating snippet → atomic+executable journal step (code in params) → `rollback_to 0` with NO force → `replay` re-ran it and skipped the read-only step → exact geometry restored.
- **Step journal (steps panel + review loop)**: a *second*, FreeCAD-side log, distinct from the MCP session above — it must survive with the RPC server stopped, so it lives on the document as the `App::PropertyString` `MCP_StepJournal` (JSON: `{version, meta, records}`). `step_journal.py` is the pure model (no FreeCAD import, unit-tested from `tests/`): `StepRecord` + planned/done/failed arithmetic + the review helpers `plan_reject`/`set_accepted`/`update_planned`/`insert_steps`/`invalidates_plan`, plus the sync pure half — `FEATURE_SYNC` (per-op property map incl. datum/sketch `AttachmentOffset`→`offset`), `tracked_objects` (which done step owns which object property), `map_cell_value` (spreadsheet `getContents()` → spec value: `=` prefix = formula, a LEADING apostrophe marks text with the builder's double quotes persisting in the cell text, else float — `Sheet.get()` returns the STALE pre-recompute value at event time, so only `getContents()` is usable), `map_constraint_value` (sketch constraint → spec: live expression binding wins whitespace-normalized, else float with `math.degrees` for angles — constraint `.Value` reads back RADIANS), and `params_for` passes ALL keys through (the old whitelist silently stripped assemble's `mates`). **Step labels are one grammar** (`step_label`/`feature_detail`/`describe_step`/`derived_label`): the caller's `cad(description=…)` IS the row label (first line only) because it is the step's intent, and with none the label is derived as `<verb> '<target>' <detail>`, the detail being the op's one identifying parameter (`pad 'FlangeProfile' 6mm`, `pattern 'BoltHoleCut' polar ×8`, `sketch 'S' 1 geom / 2 con`, `batch ×5: pad, pocket, fillet`). That description reaches the addon inside the op payload — `spec["description"]` for features, `obj_data["description"]` / `{"description": …}` for create_object/edit_object — and `create_feature` strips it before the builders and `describe_feature` see it, so intent never becomes geometry. One builder serves both a committed step's label and a planned step's `describe_step`, so planned and done rows agree instead of drifting; `tooltip_text` appends the derived label when the row IS a description, which is then the only place the operation and its parameters survive. **An execute_code step's label is one string everywhere** (`sj.execute_code_label`): the snippet's leading comment block first line, then what the code did — `"琴身轮廓 · read-only"`, or `"execute_code: read-only"` for a snippet with no comment (and for journals written by an addon older than this). Before that, the panel composed `"<comment> · <effect>"` in `row_text` while the RECORDED label was the effect alone, so `step_control(status)` and the MCP journal snapshot showed a different name for the same step than the panel did — the doc said the label came from the comment and the reply said otherwise. `row_text` still composes for a legacy label (it checks whether the stored label already starts with the description) and `step_description` keeps reading the comment off the CURRENT params, so editing the comment still updates the row. `from_json` upgrades the pre-grammar auto labels (`<op> on '<target>'`, `batch (N ops)`, `create <type> '<name>'`) to the derived form on read, so a model built before the change reads as steps without a rewrite — a caller's description never matches those shapes, so the upgrade is lossless. Ops outside the grammar (assemble, set_anchors, align_shapes, assembly) keep the richer label they already write, and `derived_label` refuses to touch them. The wording convention for the model lives in `operation_help("step_labels")` and the ASSET_CREATION_STRATEGY prompt; the `cad` docstring only points at it, to stay inside the docstring budget. `step_engine.py` is the FreeCAD half (GUI thread): `apply_op` is the single entry point shared by the RPC handler `journal_op` and the panel, and every mutating result carries a compact `journal` snapshot (counts, drift, per-step state) so clients need no follow-up `status` call. `step_control` verbs: run_next/run_all/run_to, rollback_to (records return to `planned`), reexecute (params merge; it reports `rewound` + a `warning` naming how many DONE steps after the target went back to `planned` — a re-run needs a clean base, and the silent version of this looked like "my model disappeared" — and it applies `params.label` to the record instead of merging it into the op's params), accept/unaccept (soft lock), reject (undo the step and DROP it and everything after — uniform with "a new commit invalidates the planned tail"), update (edit a planned/failed step in place; `params.label` ALONE also renames a DONE step, because a label is presentation rather than history and a wrong row must be fixable without re-running the step — `sj.set_label`), insert (into the planned tail only — the tail is insert/append-only, never edit history), replay (rollback to 0 + re-run: rebuild the model from the journal), snapshot, clear_plan, reset (it only empties the log — it never touches the document, the undo stack or any object's visibility, which is what a "reset turned my parts invisible / undid my colours" report needs to hear), status (`params.summary=true` → one compact row per step (index/state/operation/label/accepted/executable/result, no params), `params.limit`/`params.offset` → page the full records; a long session's full records — every inspection step carrying its whole snippet — ran to tens of KB that the caller paid for as context). `replay` rolls back to 0 FIRST, so a re-run failure leaves the document holding only the steps that re-ran: its result now carries `document_objects` and a warning saying the model is not the pre-replay state, and the MCP layer prints that plus the object list instead of a bare error (live: an agent's failed batch step left 0 objects while the error text said nothing). `batch` steps are executable, and so are mutating `execute_code` steps (the snippet is stored in `params["code"]` and re-run through `rpc_server.exec_snippet`, so replay rebuilds an execute_code-built model); a read-only `execute_code` stays non-executable and is skipped. The same rule governs a PLANNED snippet: `build_record` marks `execute_code` executable when the step carries its `code` (`_execute_one` re-runs recorded code through the RPC executor, so the op name alone being absent from `EXECUTABLE_OPS` was the whole reason a planned snippet was accepted and then silently skipped at run time — reported as `skipped: no recorded code`/`not re-executable`), and `set_plan` REFUSES a bare `{"operation": "execute_code"}` with no code, since it could never run. Journal writes happen INSIDE the step's transaction, but FreeCAD's undo does NOT restore document-level properties, so rollback/reexecute reconcile the log explicitly (`sj.rewind`) — that reconciliation is the primary mechanism, and `drift` (anchored on `sj.last_atomic_done`, the last transaction-bearing step) flags a manual Ctrl+Z. `plan_rollback`/`plan_reject` count only TRANSACTION-BEARING records for `undo_count` — a non-atomic record owns no undo entry, and counting it would eat an earlier step's transaction off the plain stack. `_rollback` then VERIFIES what undo actually did instead of trusting the count (the stack is shared with the GUI; an interleaved manual transaction pops under the rollback's name while the count still matches): objects the post-target steps created must be gone and journal-built objects expected at the target must be present. Removal/verification sets come from `sj.created_since` — per-record `objects_before`/`objects_after` DIFFS, never whole-snapshot subtraction (every `objects_after` lists the entire document, so at index 0 the target snapshot is empty and whole-list subtraction deletes objects that predate the journal — the user's own work; live-caught data loss, fixed in v0.5.4). On short count, stranded steps (`sj.steps_without_undo`), leftover or missing objects it escalates: `restored: rebuild` (remove `created_since(records, 0)`, reset done AND failed records to planned — a failed step's transaction aborted, so re-running is safe, and skipping it would run a later step against a missing dependency — then re-run 1..to_index; the NATIVE path does the same for failed records since 2026-10-06 (`sj.replan_failed`, reported as `replanned`): it used to rewind only the DONE ones, so after a rollback the failed records stayed failed and the cursor stepped over them (live: the user's own plan run, where a rollback to step 3 followed by Next skipped a failed pocket and pattern and ran the move and batch steps on a part missing both); a failed re-run returns `success: false` honestly), or `restored: partial` when `unrecoverable_steps` (mutated, not executable, at/before the target) blocks a rebuild — remove the doomed steps' objects and warn that their property changes cannot be restored. A clean undo reports `restored: native`. `reject` removes `created_since(index-1)` unconditionally (its records are being DROPPED, so no rebuild exists) and warns about leftovers; `reexecute` refuses when the undo came up short or left later steps' objects behind, pointing at `rollback_to`. The panel's `_apply` prints result `warnings` (red) after a success, so a rebuild/partial degradation is visible in the dock, not only in the MCP reply. `blocking` (force required) is `not atomic AND mutated`: a record that provably changed nothing (a read-only `execute_code`, `mutated=False`) cannot make undo revert the wrong change, so it must NOT stand in rollback's way — otherwise trailing inspections made every rollback demand `force`. Accepted steps are a soft lock: `rollback_to`/`reexecute`/`replay` refuse to cross one without `force=true`; `reject` does not (it is the deliberate act of destruction). `reject`/`rollback` across a mutating non-atomic record needs force. An `execute_code` commit only discards the planned tail when it actually changed the object set (`sj.invalidates_plan`) — a read-only inspection must not delete the user's plan. Read-only inspections are APPENDED at the very end, even behind a pending plan (v0.5.11): the old insert-before-the-tail shifted every planned step's index, so an MCP client that read "pocket = step 11" and then called `reexecute(11)` hit the inspection instead (live: JTest). Done records behind the plan are harmless because the plan cursor (`next_runnable`) walks by STATE and `run_to`'s upto bound is the cursor (`rec.index > upto`), never a done-count — the done-count comparison is exactly what broke under trailing done records and motivated the old insertion. Consequence: the plan is no longer guaranteed to be a trailing run (a snapshot marker can sit behind it too), so plan invalidation (`record_commit`, `append_execute_code`, `clear_plan`, `set_plan`) keys on STATE via `sj.drop_planned` — slicing from `planned_tail_start` removed nothing and let a stale plan survive a commit (live-caught latent bug). `insert_steps` bounds follow the planned RUN (`planned[0]-1 .. planned[-1]`), refusing inserts that would strand planned steps behind done records. `snapshot` appends a done+accepted, non-atomic, non-executable marker (params.note, label = note or "manual baseline") for the "user modeled off-journal, LLM continues from here" flow: the accepted soft-lock transitively protects the manual work from blind rollback, `objects_before` vs `objects_after` names what the journal missed (`added` in the result), and the planned tail is KEPT (a snapshot is a marker, not a commit). `params.accept_done` accepts every done step in the same call (bundling "everything so far is correct" into the baseline instead of ten accept clicks), and its `objects_before` anchors on the LAST DONE record's snapshot — the physical last record may be a planned tail, which never ran and carries no snapshot, and anchoring there would mark the user's whole document as "new". The dock (`step_panel.py`) drives `step_engine` directly (works with the RPC server down): status-dot list, progress bar, inline JSON parameter editor, a persistent timestamped log console (every action result, successes dim/plain and failures red — the single place outcomes land, never duplicated in the footer), context menu, and per-state action enablement. Steps/Details/Log are QSplitter regions the user can re-partition freely (sizes persist in `cadpilot_settings.json` as `step_panel_splitter`, debounced on drag). Run-op failures name the failing step (`step 3 (boolean): ValueError: ...`) in the result error, so `get_addon_log` stays LLM-debuggable; the panel also mirrors journal failures caused outside itself (MCP step_control) into its log, deduplicated against its own action narration via `_in_apply`. **Manual-edit sync**: `step_engine`'s document observer (installed at import, reload-safe singleton) mirrors GUI edits on objects a done step produced back into that step's `params["obj_properties"]` — human corrections survive reexecute/replay (object -> journal; the reverse is reexecute). Scope: for `create_object`/`edit_object`, scalar keys already present in the params (the spec's structure is never invented) PLUS `Placement` — always tracked, because a reexecute re-applies obj_properties and would otherwise teleport the part to the origin; Placement is written in the property_mapper convention (Angle in DEGREES — `Rotation.Angle` reads back radians, so `_placement_json` converts, or a round-trip turns 90° into 1.57°), and is NOT claimed when a `move` step targets the object (a move is relative; an absolute create-time Placement plus the move would double-apply). For feature ops a fixed per-op map (`sj.FEATURE_SYNC`: pad/pocket Length/Reversed/Midplane, revolution/groove Angle/Reversed, thickness Value/Reversed, draft Angle, loft Solid/Ruled, sweep Solid, fillet/chamfer Radius/Size→radius/size, datum_plane and sketch AttachmentOffset→offset — pure-z attachments only) applies, filtered to keys present in the params. Beyond scalar props the observer also syncs: `variables` spreadsheet CELLS (a `('Vars','cells')` change re-reads every `[alias, value]` pair in the params through `getContents()`/`getAlias`), `sketch` CONSTRAINT VALUES (on a `Constraints` change, only when the live constraint list still matches the params pairwise by type — a geometry edit that adds/removes constraints skips the whole sketch rather than mis-syncing), a `move`-owned object's Placement (folded into the LAST move step's obj_properties as an absolute `{"placement": ...}` — the builder's placement wins over translate/rotate, so the fold is correct regardless of the prior chain), and EXPRESSION BINDINGS both ways (a property/constraint bound in the GUI syncs as `"=expr"` whitespace-normalized from `ExpressionEngine`; unbinding falls back to the numeric value). FreeCAD ≥1.1 keeps fillet/chamfer sizes in per-edge `Edges` tuples instead of a scalar property, so `Edges` is claimed too and syncs only when all tuples share one size (`_uniform_edge_size`) — per-edge sizes have no spec representation. When several done steps touch one object, the LATER step owns each property. Batch records are covered too: `tracked_objects` claims create/edit/move SUB-OPS (property claims carry `(index, key, sub)` and `_sync_props_target` routes the write into `params["ops"][i]["obj_properties"]`; a batch move sub-op receives the drag fold), so a manual correction on a batch-created part survives replay instead of being silently reverted — feature sub-ops stay unclaimed (their created object cannot be attributed from the record-level diff). Syncs are logged to the addon log (`journal sync: step N obj.prop = v (manual edit)`) and surfaced in the panel log via `pop_sync_events`. The observer must ALSO ignore engine-driven property writes: undo/redo/re-runs restore OLD values, and mirroring those back is how a reexecute silently reverted a manual correction (live-verified: Height synced to 10, reexecute undid the edit's transaction, the observer "manual-edited" the journal back to 6, the re-run rebuilt at 6). `_EngineQuiet` (module flag `_ENGINE_ACTIVE`, public wrapper `engine_quiet()`) mutes `slotChangedObject` across `_stack_op` (undo/redo), `run_record`'s execute/abort/final-recompute windows, AND every RPC mutation (`_run_op_with_screenshot` wraps `gui_fn()`, `execute_code` wraps `exec_snippet`) — an RPC mutation is its own journal step, so letting it bleed into an EARLIER step's params made reject/replay inconsistent; a genuine GUI edit never happens inside one of those windows. The aborts inside `rpc_server.py` are deliberately NOT muted — they restore values the params already describe, so the diff check swallows them (and a failed snippet's sync rolling back with its transaction is correct). **Empty-commit downgrade**: after every commit, `downgrade_if_no_undo` compares `doc.UndoCount` against the pre-op value — a commit that produced no undo entry (a read-only op like `assembly verify`, a same-value edit) rewrites the record to non-atomic/non-mutated/non-executable with `transaction=""`, because a phantom transaction claim would make `plan_rollback` pop an EARLIER step's entry off the shared undo stack (`run_record` applies the same probe to re-runs, generalized from the old execute_code-only check). One producer-side trap this exposed: `AssemblyObject.Shape` (and App::Link composites) rebuild LAZILY on first access, not on recompute — after a mate/solve, the next transaction to READ that Shape (typically a read-only `verify`/audit) absorbs the rebuild write and earns a phantom undo entry; `_settle_shapes` (joint_ops) reads the caches at the end of every mutating assembly op so the rebuild is charged to the op that caused it (live-verified: the first verify after a mate produced UndoCount +1 before the fix, is cleanly downgraded after). It is deliberately glyph-free: actions are text-only (the platform's standard icons clash with FreeCAD's chrome) and step states are runtime-painted dots. The styling is MATLAB-inspired — flat sections, hairline separators, one accent — from two hand-tuned palettes (dark/light), chosen by sampling a rendered main-window pixel, because FreeCAD themes are app-level stylesheets that leave the QPalette light even in dark mode (never trust `palette()` for theme detection). The dock is looked up by `objectName` with duplicate collapse, because `findChild(PanelClass, …)` matches on the class object and misses docks built before a hot reload (see `tests/test_addon_gui_wiring.py`). A SKIPPED record (`_run_steps` marking a non-executable step done) used to keep `atomic/mutated=True` while owning no transaction, which made it satisfy `sj.steps_without_undo` and diverted an otherwise clean native rollback to the destructive rebuild path over a step that provably changed nothing; the skip path now clears both flags and the transaction (live-verified: a planned `get_topology` skipped, then `rollback_to` reported `restored: native`, `stranded: []`).
- **Addon diagnostics (`get_addon_log`, `diagnose`)**: `dbglog.py` ring buffer + rotating file under FreeCAD's user data dir; the RPC handler is deliberately NOT GUI-dispatched, so the log stays readable exactly when the GUI thread is wedged and every other call hangs. `request_log.py` tags records with the RPC (`req#N`) that caused them, including work carried onto the GUI thread. - **InitGui.py bare-exec trap**: FreeCAD runs `InitGui.py` with a bare `exec(code)` into a namespace that is NOT the `__globals__` of the functions the file defines, so a module-level name is invisible inside `_bootstrap()`'s nested helpers (only their enclosing function's closures and builtins resolve). - **Batch integrity (v0.5.14)**: `execute_operations` removes objects a FAILED sub-op already created (inside the batch's own transaction; the per-op result carries `removed_debris` and a note that already-applied property writes stay) — a failed `pad(length="abc")` used to commit a valid default-length Pad while its result said `success:false`, and a failed boolean left a Touched/Invalid `Cut`. - **Appearance (`cad(operation="color")`, live-verified on 1.1.4)**: FreeCAD 1.1 has NO `ShapeColor` in a ViewObject's `PropertiesList` (the list holds `ShapeAppearance`, a `PropertyMaterialList`, plus `Transparency`/`LineColor`/`LineWidth`/`DisplayMode`), yet reading and writing `view.ShapeColor`/`view.Transparency` both work and write THROUGH to `ShapeAppearance[0].DiffuseColor`/`.Transparency` — the persisted per-shape material (proved by save → close → reopen → read). That is what makes the op possible at all, and why the color is written with the legacy names: same path the GUI's color dialog takes. **A ViewObject write inside a document transaction DOES produce an undo entry** (UndoCount 1→2, named `CADPilot: color <obj>`), so a color step is rollback-able/replayable like any other; the step changes no object set (`objects_before == objects_after`), so the object-set verification cannot catch a wrong undo for it — `_undo_trust`'s name comparison is the only guard, which is why the transaction name must keep matching `_transaction_name`. `color` is a feature op (builder `_build_color`, `FEATURE_TYPES`/`_BUILDERS`/`_DERIVED_OPS`/`describe_feature`) purely to inherit that machinery, but `create_feature_gui` must early-return for it exactly like `move`: the recompute/Invalid-Shape/negative-volume checks have nothing to say about a repaint and would refuse a color on a leftover or a Plane. Target resolution: one name, a list via `obj_properties.objects`, or `*`/`all` for the document; a PartDesign feature redirects to its owning Body (a feature's ViewObject is hidden, so coloring it changes nothing visible), reported per object in `colored`. Colors go through ONE parser (`property_mapper.parse_color`, shared with `create_object`/`edit_object`'s ShapeColor and LineColor/PointColor): `[r,g,b(,a)]` floats 0..1, INTEGERS > 1 as 0-255 (the integer rule is what keeps the scales apart — a float `[1.4,0.2,0.2]` is an error, not 1.4/255), `#rrggbb(aa)`, a name. Out-of-range channels are refused, not clamped: FreeCAD stores them as given and clamps only at render time, so the write "succeeds" invisibly. The op reads every value back off the view provider and FAILS the step on a mismatch, so a repaint that did not stick can never read as success. Two live-caught traps: `_build_color` needs `global _LAST_FEATURE_INFO` (without it the assignment bound a local and `colored` came back `[]` on every call — invisible to the fake-connection tests), and `openDocument` on an already-open file returns the SAME document, which silently turned a save/reopen persistence test into a same-object read (close first, or the reopened `Name` is still the old one). GUI-side color edits are NOT synced back into a color step's params (the observer watches the App document, not view providers), so reexecute/replay re-applies the recorded color. **Rendering (pixel-sampled, not eyeballed)**: the 3D view draws the PartDesign **Body's** node (hiding the Body hides the whole part; hiding the tip feature changes only the material, it does not remove the solid), and two FreeCAD behaviors make a *stored* colour differ from the *drawn* one. (a) Creating any PartDesign feature that becomes the Body's Tip rebuilds that node with FreeCAD's DEFAULT material, so an earlier colour visually VANISHES while `ShapeColor`/`ShapeAppearance` still report it (live: red body (185,45,45) → after a fillet the view drew (110,116,120)). Fix: `create_feature_gui` calls `_refresh_appearance(body)` whenever the new feature is the Body's Tip; re-assigning the appearance with a FRESH `Material` (an identical assignment is a no-op for FreeCAD, so no rebuild) restores it (live: → (184,45,44)), and a genuine per-face list is left untouched (`_uniform_material`). (b) A `ShapeColor` write does NOT repaint an object whose `ShapeAppearance` holds MORE THAN ONE entry: the stored materials all become the new colour while the view keeps drawing the previous one (live: two writes on a 3-entry appearance, stored green / drawn blue). The color op therefore collapses a multi-entry list to ONE uniform entry (its own whole-object semantics) and reports `normalized_appearance: "N materials -> 1 uniform"`, which is also what forces the repaint. Verifying a colour without a screenshot is therefore not enough: `get_view` + sampling a pixel of the part is the only proof.

- **Batch step re-execution**: `cad(operation="batch")` sub-ops use the RPC schema's `{"action": ...}` key and are journaled verbatim, while journal-native steps use `{"operation": ...}`. BOTH sides accept both keys — `sj.sub_operation()` is the single reader on the re-execution side (so journals written by an older addon are repaired rather than rejected), and `_run_one_operation` tolerates `operation` on the initial run (else a journal-native batch replays fine but dies "unknown action: None" the first time). The old failure ("operation '' is not re-executable") undid the step and then failed to re-run it, leaving the model stuck one transaction behind, which is what "roll back cannot go back" looked like. `run_next`/`run_all`/`run_to`/`replay` skip non-executable records (execute_code inspections are normal journal citizens): the record is marked done with result `skipped: not re-executable`. - **Reopen safety (journal vs. undo stack)**: the undo stack does not survive a reopen, and a file saved under a new name reopens as a document named after the FILE (saveAs does NOT rename in-session; the Name changes only on reopen) — both facts together made rollback unusable on any saved-and-renamed model (live: DeskFan.FCStd, ex-MideaDeskFan, where every rebuild step died `Unknown document 'MideaDeskFan'`). Two guards in `step_engine.py`: (a) `_replay_ready_code` rewrites a replayed snippet's `getDocument('<old>')` literals to the host document when the old name no longer resolves (pure helpers `sj.document_refs`/`sj.rewrite_document_refs`; a name that IS open is left alone — the snippet may genuinely mean that other document); (b) `_undo_trust` compares the top of `UndoNames` (index 0 = next to be undone, ghost entries filtered) against the journal's own transactions for those steps BEFORE popping, and answers with the SPAN the stack can still vouch for rather than a yes/no: FreeCAD CAPS the stack (`MaxUndoSize`, 20 by default, so once it is full every commit evicts the oldest entry), and a journal longer than the cap can never supply the whole span again. Reading that shortfall as "the undo stack does not hold the journal's transactions" (the reopened-document verdict) popped nothing and forced a full rebuild on every rollback deeper than the cap, while every surviving entry matched the journal exactly (live-caught: a 24-transaction journal rolled back to 0, where the top 20 `UndoNames` were identical to the journal's). The span is what gets popped; a genuine shortfall still routes to the rebuild path, but the reason now names the real cause (the cap, or a foreign transaction in the way) instead of blaming a reopen, and the "still present" trigger only guesses at an off-journal edit when the stack was otherwise complete. What this closes is the property-only blind spot where undo popped the WRONG transaction and the object-set verification saw nothing (no objects move when only properties change) — the reason a full-span stack with a foreign entry in it still refuses to pop past that entry (pure half: `sj.undo_trust_span`, unit-tested).
- **Multi-agent sharing**: every MCP client process talks to the same FreeCAD over XML-RPC, and concurrent agents interleave on the one GUI thread — so every active-document-dependent channel must be bound to an EXPLICIT document or the agents' work crosses. The two that were not: `execute_code` (owned the transaction, the journal step AND `App.ActiveDocument` semantics of whatever document the OTHER agent's call left active — agent B mutating ErgonomicChair could file the step in gaming_mouse's journal or leave its change outside any transaction) and screenshots (every capture grabbed the foreground tab). Bindings: `execute_code` takes `doc_name` — the addon resolves the document first (unknown name → clear error), activates it (`App.setActiveDocument` only; there is no `Gui.activateDocument` on 1.1.x and the foreground MDI tab is deliberately never flipped, so `App.ActiveDocument` inside the snippet resolves there), opens the wrapper transaction on it and files the journal step there; `execute_code_operation` binds an ACTIVE SESSION's document automatically, so session-bound agents need no new argument (an explicit `doc_name` wins). With neither, `execute_code_operation` binds this server process's HOME document (`_last_doc_name` in `operations/core.py`): the document the process last created or explicitly mutated (create_document / cad / execute_code / session(start/resume) / assemble / set_anchors / align_shapes / step_plan / step_control update it). Each MCP client spawns its own server process, so two agents that pass nothing still stick to their own document, and the reply discloses a fallback binding. `get_view` takes `doc_name`, and `save_active_screenshot` (all three capture sites: `_run_op_with_screenshot`, `execute_code`, `get_active_screenshot`) activates the named document before grabbing — mutation-attached screenshots frame the mutation's own document for free, since the wrappers know it. XML-RPC is positional, so the client only sends `doc_name` when set: old addons degrade to the legacy active-document behavior instead of faulting. The rest of the tool chain (cad, measure/topology, anchors/assemble, step_control, sessions) already documents its doc_name. Prompt-side guidance lives in `operation_help("multi_agent")`; hard isolation (separate undo stacks, mutual invisibility) still means two FreeCAD instances on different ports. One FreeCAD-level trap belongs to this bullet: the undo stack is NOT document-isolated (see the ghost-entry note under Modeling sessions) — a second document's transaction may appear on your stack rendered `-> name`; it is skipped without counting, and after the fix no new ghosts are produced.
- **Knowledge hierarchy**: prompts instruct ① model's own knowledge → ② `recall_patterns` → ③ `inspect_freecad`; successful approaches are stored via `save_pattern`/`session(action="complete")`.
- - `property_mapper` reaches two dynamic/awkward cases: `{"cells": {cell: [alias, value]}}` on a Spreadsheet is handled FIRST (the object does have a property literally named `cells`, but assigning it fails with "Invalid type" — the shared `set_spreadsheet_cells` writes cell by cell and is also what the `variables` op uses), and `Placement` accepts `[x, y, z]` as well as the dict form (a list used to die with "'list' object has no attribute 'get'").
- **Name sanitization**: FreeCAD sanitizes document/object names (spaces → underscores, deduplication). RPC handlers return the *actual* name from FreeCAD, not the requested name.

## Coding Conventions

- Python 3.12+ (uses `X | None` union syntax, `type` alias).
- Logging: use `logging.getLogger("CADPilotserver")` in both MCP server and addon code.
- Tool operations: each tool has a dedicated `_operation` function in `operations/core.py` that takes a `FreeCADConnection` as its first arg and returns a `ToolResponse` (`list[TextContent]`).
- Addon code uses `FreeCAD.Console.PrintMessage/PrintError/PrintWarning` for FreeCAD's Report View.
- Settings persisted as JSON via `cadpilot_settings.json` (in FreeCAD's user data dir).
- **Docstring budget (prompt economy)**: every `@mcp.tool()` docstring is injected into the AI client's context on `tools/list`. Keep docstrings to a 1-3 line summary + brief Args (drop zero-information lines like "doc_name: Document name."; inline short Returns) — long parameter/semantics references go in `src/cadpilot/tool_docs.py` (`CAD_OP_DOCS`) and are served on demand via the `operation_help` tool. `tests/test_operation_help.py::test_tool_docstring_budget` enforces a total budget (9,000 chars at the current 27 tools, +150 per added tool); it fails if docstrings creep back up.
- **MCP surface conventions (mcp-builder)**: every `@mcp.tool()` carries `annotations` (title + `readOnlyHint`/`destructiveHint`/`idempotentHint`/`openWorldHint`) so a client can tell introspection from a mutation; the `_read_only`/`_mutating` helpers in `server.py` keep the classification in one place (`openWorldHint=True` for anything reaching FreeCAD over XML-RPC, `False` for the purely local `operation_help`/`recall_patterns`). Numeric/range params use `Annotated[..., Field(ge=…, le=…)]` so constraints land in the generated JSON Schema (validated at the tool boundary; the addon still clamps defensively). Listing tools (`get_objects`, `list_documents`, `session(get_steps)`, `get_topology`, `get_addon_log`) return a spec-shaped page (`total`, `count`, `offset`, `has_more`, `next_offset` plus the items under their domain key `objects`/`documents`/`steps`) built by `operations/core._page_envelope`. Resources expose the semi-static references without a tool call: `cadpilot://operations`, `cadpilot://docs/{operation}` (template), `cadpilot://patterns`, `cadpilot://patterns/{pattern_id}` (template). `tests/test_tool_surface_meta.py` pins all of it; `evaluations/` holds the Phase 4 read-only QA pairs. Deliberate deviations from the guide: failures stay inside the result (`success:false` + diagnostics) rather than protocol-level `isError`, because that guidance text is the payload an agent needs and a raised error would hide it; handlers stay sync `def` (FastMCP runs them on a thread pool), so there is no async `ctx.report_progress`; no `outputSchema`/`structuredContent`, to keep the `mcp.server.mcpserver` 2.x fallback working; the server name stays `"CADPilot"` rather than `cadpilot_mcp`, since clients namespace by server and renaming would break existing configs and docs.

## Adding a New MCP Tool

1. Add the operation function in `src/cadpilot/operations/core.py`.
2. Export it from `src/cadpilot/operations/__init__.py`.
3. Add the `@mcp.tool()` handler in `src/cadpilot/server.py` that calls the operation.
4. Add the corresponding RPC method in `addon/CADPilot/rpc_server/rpc_server.py` (on the `FreeCADRPC` class).
5. Add the client proxy method in `src/cadpilot/freecad_client.py`.
6. If the tool touches the document/GUI, dispatch via `dispatch_to_gui()` in the addon.
