# CADPilot 设计文档

[English](DESIGN.md) | **中文**

CADPilot 让 AI 客户端直接驾驭 FreeCAD：创建文档、构建全约束草图和参数化特征、装配零件，并用真实的测量值验证结果。这份文档讲清楚系统是怎么搭起来的、每个决定背后的原因，写给想理解它、修改它，或者想做个类似东西的人。

## 1. 设计想达到什么

四个目标决定了后面所有的取舍。

**完整的控制力。** 用户在 FreeCAD 窗口里能做的事，AI 都应该能做：建对象、改对象、画草图、加特征、装配、测量。

**省上下文。** 每个工具定义、每条回复都会占用模型的上下文。CADPilot 把工具列表压小、把 docstring 写短、默认只回文字，这样一场很长的建模对话才不会被自己淹没。

**敢于试错。** 建模本质上就是试错。每一次改动都必须可以撤销，AI 才能大胆试一个方案、退回来、再换一个，而不是从头重建。

**人始终在场。** 用户就坐在 FreeCAD 窗口前看着模型一点点长出来。他要能看懂 AI 做了什么、亲手改一改，然后让 AI 接着自己的改动继续做。把这件事做好本身就是一个子系统，见第 5 节。

## 2. 两个进程

```
AI 客户端（Claude Code、Cherry Studio 等）
   |  MCP over stdio
   v
cadpilot MCP 服务器（src/cadpilot，Python >= 3.12，经 uvx 启动）
   |  XML-RPC over TCP，localhost:9875
   v
FreeCAD 插件（addon/CADPilot，活在 FreeCAD 进程里）
   |
   v
FreeCAD 文档 / GUI
```

MCP 服务器和插件是两个独立程序，靠 XML-RPC 通信，原因有三。

**隔离。** MCP 服务器绝不 import FreeCAD，所以它可以跑在任何地方，包括另一台机器（用 `--host` 指过去）。FreeCAD 重启后，服务器会察觉连接已断，重建代理并重试一次。

**生命周期对不上。** AI 客户端想启动、终止 stdio 服务器都随它，而 FreeCAD 是个长寿命的 GUI 程序。插件握着 CAD 状态，MCP 服务器来了又走，CAD 状态不受影响。

**库兼容。** 服务器优先从 `mcp.server.fastmcp` 导入 `FastMCP`（MCP 1.x），失败则回退到 `MCPServer`（MCP 2.x）。

XML-RPC 的传输超时是 150 秒。socket 超时**不会**重试，因为操作可能还在 FreeCAD 那边执行着，重试会做两遍。

## 3. FreeCAD 只容得下一个线程

FreeCAD 的文档树和 GUI 不是线程安全的：文档操作必须在主线程做，而 XML-RPC 服务器跑在自己的线程上。插件负责把每个请求转交过去，这件事的每个细节都值得小心。

调用进入队列，RPC 线程阻塞等待结果。每次调用都有**自己独立的应答队列**，所以某次调用超时绝不会把答案串到下一次调用头上。主线程靠 Qt 信号立刻被唤醒，另有一个定时器兜底，防止信号万一丢失。

插件不去打扰用户：鼠标按住、或者对话框开着时，排队的任务会先等一拍，自动化操作不会在用户拖拽到一半时突然插进来。鼠标检查有个故事：后台启动或远程桌面会话之后，Qt 会报告一个根本没人按下的鼠标键，而程序无法清除这个状态，于是队列永远在等待。表现为 `ping` 一直正常，所有真实调用全部超时，看起来就像断线了。现在这个等待只在主窗口确实处于活动状态时才生效。

队列任务里的异常会被捕获，写进 FreeCAD 的报告视图，并作为错误信息返回给调用方，循环本身不会被杀死。停服时用一个哨兵值阻止定时器继续排班，服务器才能真正停下来。

`execute_code` 提交的代码运行在插件命名空间的**副本**里，用户代码里的赋值不会污染服务器自己的变量。

## 4. 工具面怎么设计

### 4.1 一个 `cad()` 工具，而不是三十个

客户端列出工具时，每条工具定义都会被注入模型的上下文，不管模型最后用不用。工具面太宽等于还没开工就先花钱。所以所有改动收敛到一个 `cad(operation=...)`，具体操作作为普通参数传入：

* 对象级：`create_object`、`edit_object`、`delete_object`、`batch`
* Part 特征：`boolean`（可同时多个工具体）、`fillet`、`chamfer`、`loft`、`sweep`、`mirror`、`pattern`、`move`
* Sketcher 与 PartDesign：`variables`、`sketch`、`pad`、`pocket`、`revolution`、`groove`、`thickness`、`draft`、`datum_plane`、`hull`

### 4.2 docstring 是要花钱的

docstring 在每场对话里都占 token，所以每个 `@mcp.tool()` 的 docstring 只写一至三行摘要加简要参数说明。每个操作的详细参考放在 `tool_docs.py`，模型真正需要细节时通过 `operation_help` 按需取。有一个测试保证 docstring 总量不超过 11000 字符，防止这里悄悄膨胀回去。

### 4.3 知识的次序

提示词告诉模型先查哪里：先用自己的知识，再查 `recall_patterns`（一个持久化的"成功套路库"），再查 `inspect_freecad`（在运行时列出对象的属性方法或某个模块的 API）。验证有效的套路再用 `save_pattern` 或 `session_complete` 存回去，下一场会话起点就更高。

## 5. 处处可撤销：事务、会话与步骤日志

每个已提交的改动都运行在 FreeCAD 事务里。其上有两套日志，回答不同的问题：**建模会话**在 MCP 这边，覆盖整场对话；**步骤日志**在 FreeCAD 那边，是用户看得见、也能亲手驱动的评审循环。

### 5.1 建模会话

会话（`session_start` 到 `session_complete`）把每次改动记成一步：做了什么、参数是什么、结果如何、之后文档里有哪些对象、模型或用户还附了什么笔记。那份对象清单是指纹，用来判断文档和日志还吻不吻合。

回滚到第 N 步就是 `doc.undo()` N 次加日志截断，不用删了重建。被回滚的步骤放进重做缓冲区，等新一步到来才清空，和 FreeCAD 自己的重做行为一致。

每次已提交的改动还会被自动审计：一条只读的连通性检查在每次 `cad()` 之后运行，报告哪些零件脱离了整体。审计只警告、不拦截，可以全局关闭，超大文档时也会自动跳过。

会话和模式以 JSON 存在 `~/.cadpilot/`（或 `$CADPILOT_HOME`）下，先写临时文件再改名，崩溃不会截断已有数据。

### 5.1.1 让 `execute_code` 可以撤销

这一节值得单独讲，因为它改变的是日常手感。

在 FreeCAD 里，直接改属性**不会**产生任何撤销条目，撤销条目来自事务。一个靠写代码片段建模的 AI（大多数都这么干，因为 `execute_code` 是最灵活的工具）产出的工作没有任何回滚够得着，日志里堆满阻挡一切回滚尝试的步骤。

现在插件把每段代码都包进一个事务，结束后报告这个事务**是否真的产生了撤销条目**。

* 文档变了：这一步记录为普通的原子步骤，占且只占一条撤销条目，代码随步骤保存，于是回滚、重跑、整体 replay 全部可用。一个完全用代码建出来的模型，重放起来和一个用声明式操作建出来的没两样。
* 什么都没变：空事务提交是免费的，因为空提交不产生撤销条目。这一步记录为只读，不阻挡回滚，也不会被重跑。
* 代码抛异常：事务被中止。失败的运行不会留下改了一半的残骸，这是顺带修好的第二个问题。

事务不嵌套，所以片段自己管理事务时只是合并进这层包装。包装只在当前没有未决事务时才开新事务。

### 5.2 步骤日志与 Steps 面板

会话随 MCP 服务器一起消失，坐在 FreeCAD 前的人也完全看不见它。**步骤日志**是第二套日志，直接存在文档上（`MCP_StepJournal` 属性），RPC 服务器停了它也在。一套引擎被两个前端驱动：

* `step_control` 工具，动词有：`run_next`、`run_all`、`run_to`、`rollback_to`、`reexecute`（先撤销该步，再带上合并后的参数重跑）、`accept` 与 `unaccept`、`reject`、`update` 与 `insert`、`replay`（退回起点，从日志重建全部）、`snapshot`、`reset`；
* FreeCAD 里的 **Steps 面板**，带步骤列表、进度条、可编辑的参数视图和日志控制台。MCP 服务器不在它也照常工作，甚至可以事后打开一个保存过的文档，重放它是怎么被造出来的。

几条规则让这套循环敢用：

* 日志写在每步的事务里，但 FreeCAD 的撤销不恢复文档级属性，所以每次回滚和重跑都要手工对账。`drift` 标志锚定在最近一个带事务的步骤上，靠它发现用户按过 Ctrl+Z。
* 撤销条目数只统计带事务的步骤。只读步骤没有事务，把它算进去会从撤销栈上弹掉更早一步的事务。
* 只读步骤也不阻挡回滚，因为它可证明什么都没改。真正挡路的是"可能改了文档却没有事务"的步骤，强行越过它是调用方的明确决定。
* 用户接受过的步骤是软锁：回滚、重跑、replay 想跨过都要传 `force=true`。`reject` 是有意销毁，所以畅通无阻。
* 同一个操作名有两种写法：batch 的子操作照 RPC schema 原样记成 `action`，而为日志亲手写的步骤用 `operation`。读日志的和首次执行的两侧都认两种写法，旧日志因此被修复而不是被拒绝。
* `run_all` 和 `replay` 会跳过无法重跑的步骤并如实上报，而不是让整趟失败。每条改动类回复还带一份紧凑的日志快照，调用方很少需要再单独查一次状态。

### 5.3 人和 AI，两个方向都要通

日志存在是为了让两边都能动手。用户在属性面板里改了一个尺寸，文档观察器会把这个改动**镜像回**产出该对象那一步的参数里。重跑那一步时保留的是用户改过的值，而不是把零件拽回 AI 当初写的样子。Placement 永远被跟踪，因为重跑会重放记录的参数，不跟踪就会把零件瞬移回原点；角度按度数存，与属性写入端的约定一致。特征类步骤用一张固定的属性名映射，规则是只有所有边同一个值时才镜像回尺寸，因为 FreeCAD 的圆角和倒角把尺寸存在每条边上。多个步骤碰同一个对象时，后一步拥有该属性。

`snapshot` 动词覆盖另一个方向：用户在日志之外做的工作。它追加一条"已完成且已接受、但不可重跑"的标记，这层软锁保护手工成果不被盲目回滚；它的前后对象清单则说出日志到底漏了什么。未执行的计划在快照后保留，因为快照是标记，不是改动。

## 6. 草图与参数化特征

草图在单个事务里原子建成：几何（列表顺序即约束引用的 GeoId）和约束一起提交，立刻求解。回复里带回自由度、是否全约束、以及求解器警告。规格冲突或畸形时回滚，并把求解器的诊断（比如哪几条约束冲突）原样带回。

几个值得知道的细节：

* `external` 外部几何只允许引用别的对象的起点和终点，因为引用中点在求解时必然失败，这种情况在提交前就被拒绝并给出明确提示。草图本体以外的引用目标用 `PartDesign::SubShapeBinder` 自动搭桥，因为 PartDesign 不接受体外外部几何。
* 基准面可以依附到原点平面或已有面，草图也可以依附到基准面。
* **依附草图优先用方向，别用面名。** `plane={"face": [obj, "+Z"]}`（还支持 `-Z`、`+X`、`-X`、`+Y`、`-Y`，以及 top、bottom、left、right、front、back 这些词）会挑出法向朝那个方向的平面，同向多面时挑最外侧那张。原因是 FreeCAD 每加一个特征都会重新推导面名，同一个 `Face5` 在上个特征上是顶面、到下个特征可能就成了侧壁。按名字依附可能把草图贴到侧面，pocket 什么都没切到，调用却照样报成功。作为兜底，pocket 或 groove 一点材料都没切掉时会回一条警告。
* **阵列复制的是特征，不是实体。** 对 PartDesign 特征，`pattern` 会在同一个 Body 里创建 `PartDesign::PolarPattern` 或 `LinearPattern`，把那个特征（一个孔、一条肋）作为原始项复制开。对 Part 级对象（布尔结果、基础体）则用 Draft 阵列复制对象本身。实测 FreeCAD 1.1 无法经 Python 可靠地驱动 PartDesign 阵列，所以当变换毫无效果时，操作会明确报错，而不是返回一个"要六个孔只给一个"的零件。
* **依附融合。** 草图依附在某个实体的面上时，对它做 pad 或 pocket 直接作用于那个实体：pocket 切它，pad 并进它。这种场合先 pad 再布尔减是错误做法。
* `hull` 用两三张视图轮廓草图沿各自法向拉伸后求交，造出可视外壳。结果是普通的 `Part::Feature`，重载文档后还在；同名重跑会就地替换形状，方便迭代。
* 任何属性值只要是以 `=` 开头的字符串，就走 ExpressionEngine 绑定而不是直接赋值，电子表格驱动的全链参数化靠的就是它。

## 7. 把几何读回来

`measure_geometry`、`get_topology`、`check_interference`、`get_positioning_info` 是只读的形状查询，派发到 GUI 线程且不开事务。

坐标一律是全局坐标：形状自身的存储几何里已经带了对象的摆放，所以不做手工变换（早期版本的双次变换 bug 把这条规则钉死了）。拓扑列表按尺寸排序并分页，每张面、每条边都带类型、中心、法向以及半径或轴向等信息，模型据此为圆角挑边、为草图挑面。数字保留四位有效数字，但只在出口处舍入；定位零件的计算全程使用全精度。

## 8. 怎么把零件放对位置：锚点与装配

AI 驱动 CAD 最难的问题是零件之间的相对定位。CADPilot 用数据回答，不用截图。

**锚点**给对象上的点和方向起名字。一部分自动推导（包围盒中心和各角、质心、主导圆柱面的轴线、最大平面面的中心），模型和用户也可以自定义。自定义锚点以**局部坐标**存在对象上，零件移动时它们跟着走。

**`assemble`** 接一串配合，每条指定对象、锚点、目标、目标锚点，外加模式（`center`、`touch`、`axis`）和可选偏移。全部配合在单个事务里一次落位，然后每个锚点在**新位置**重新解析，报告每条配合残余的距离和角度。任何一条超差就整体中止。

**`align_shapes`** 是单步版的同类能力：面贴面、边对边、点对点。

**`verify_assembly`** 审计整个文档：悬空的零件、空间上互相重叠的对、具名锚点对的逐项校验，以及一张利用已扫描对建立的接触图，把相互接触的零件归成组，报告脱离主装配的孤岛。

### 带持久关节的装配会话

`assembly_session` 是独立的另一台状态机，建在 FreeCAD 1.1 原生 Assembly 工作台上：先固定基准件，加组件、配、求解、验证、收尾。组件是持有摆放的 `App::Link`，关节持久存在文档里，移动父件后重新求解，子件跟着动。

几条让它可靠的规则，全部在真实 FreeCAD 上验证过：

* 求解器的准备步（matchJCS）必须在最终那次 `solve(True)` 之前跑。重复求解会弄脏求解器保存的状态。
* 组件形状是全局坐标，关节引用却是零件局部坐标，所以残差用几何方式量（面间距、法向夹角），绝不经过关节坐标系自己的数学。
* 配合可以指定面、锚点或点；指定面时由最近的顶点决定落点，这正是用户"点这里"的含义。
* `trim={"winner": ...}` 是声明式的优先级裁剪：在败方局部坐标系里烘焙一次非破坏性切割，再把 link 重新指过去。每一步都预计算自己的撤销负载，回滚就是一条合并后的请求，原子执行。
* MCP 侧先校验插件的返回再记录任何状态，失败的请求不会留下改了一半的会话。

## 9. 截图，由模型说了算

截图是可选项，默认关。单次调用可以点名要；`--with-screenshots` 把默认改成开；`--only-text-feedback` 则彻底禁止，给纯文本模型一个硬保证。改动类工具在与干活同一个请求里顺带截图，一个来回搞定；对旧版插件则退回第二次调用单独取。长边默认压在 768 像素以内，除非显式给了尺寸。少数视图（TechDraw、Spreadsheet）截不出来，返回空。

## 10. 长计算

`execute_code_async` 在后台线程跑代码并返回任务 id。状态、打印输出、异常栈保存在一个有上限的内存注册表里（最多 50 个任务），通过 `get_task_result` 轮询。后台代码用 `task_print` 或 `FreeCAD.Console` 汇报，而不是 `print`，因为从线程里重定向进程级的 `sys.stdout` 是竞态。后台代码不得碰文档和 GUI，那是同步 `execute_code` 的职责。

## 11. 信任与边界

RPC 服务器默认只听 localhost。远程访问是显式开启项，开了以后绑定到全部网卡，并由一个过滤服务器强制执行 IP 或网段白名单；非法条目在配置阶段就被拒绝。

`execute_code` 设计上就是任意代码执行。它是让系统能力完整的逃生舱，也因此威胁模型把任何能连上服务器的客户端都视为完全可信。这是这个项目有意做的取舍，也是远程访问默认关着、还套着白名单的原因。`--host` 的值在启动时校验。

## 12. 出了问题怎么办

* **重连。** 连接死了客户端就重建代理重试一次，覆盖 FreeCAD 或插件重启的场景。
* **新旧互通。** 新客户端对旧插件自动降级，旧客户端对新插件照常可用。
* **名字会被净化。** FreeCAD 会改写对象名（空格变下划线、重名加序号），所以所有处理器返回的都是 FreeCAD 实际选定的名字。
* **版本差异靠探测。** 同一设置在不同版本里存法不同时，插件在运行时探测该用哪种。
* **热重载。** 开发期间插件可以不重启 FreeCAD 就重载，停服与重启竞态的罕见情况也有成文的修复路径。
* **FreeCAD 不在也能诊断。** `diagnose` 工具完全跑在 MCP 一侧、绝不 import FreeCAD，所以 FreeCAD 没开或者卡死时它照样答题。它报告 RPC 端点、FreeCAD 进程、每个用户目录下的插件安装情况以及插件的启动日志，最后给出一个具体的处理建议。它最有用的判断是：端口在监听但 ping 不应答，说明 GUI 线程卡住了，而不是哪里配置错了。
* **GUI 卡死时插件日志照样可读**，因为它的处理路径刻意不经过 GUI 线程。它是一个小环形缓冲加一份磁盘日志文件，每条记录都标着是哪个请求引发的。
* **启动脚本陷阱。** FreeCAD 用 `exec()` 跑插件的 `InitGui.py`，这导致文件里定义的函数看不见文件顶层 import 的名字。所以启动需要的每个名字都在启动函数内部 import。这里的崩溃会被写进一个日志文件，`diagnose` 知道去哪找它。

## 13. 怎么测试

pytest 套件约 325 个测试，用一个记录每次调用的假 XML-RPC 连接覆盖 MCP 服务器侧：响应整形、截图策略、重连行为、会话与模式状态机、`cad()` 派发、装配状态机（含失败路径）、引导式建议，以及 docstring 预算。

插件离开 FreeCAD 就无法 import，所以第二层测试用 Python 的 `ast` 模块解析插件源码，钉住那些只在运行时才会静默失效的契约：`InitGui.py` 的命名空间规则、Steps 面板的信号接线、batch 子操作名的两种写法、以及 replay 的跳过行为。诊断套件覆盖各平台的路径布局、一个真实的本地端点、一个关闭的端口，以及工具能抵达的每种判定。

需要真实 FreeCAD 的部分由 `tests/live_sketch_verify.py` 做端到端验证：搭一个参数化支架，检查电子表格的值是否传播、失败时报告什么、以及撤销是否干净。
