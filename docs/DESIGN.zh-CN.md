# CADPilot 设计文档

[English](DESIGN.md) | **中文**

CADPilot 使 AI 客户端能够驱动 FreeCAD：创建文档、构建全约束草图与参数化特征、装配零件，并以真实测量值验证结果。本文档说明系统的架构与各项设计决策的依据，面向需要理解该系统、对其进行扩展，或构建类似系统的读者。

## 1. 设计目标

设计围绕四个目标展开。

**完整的控制力。** 用户在 FreeCAD 窗口中能做的一切——创建与编辑对象、绘制草图、施加特征、装配、测量——AI 也应能做。

**较小的上下文开销。** 每个工具定义与每条回复都消耗模型的上下文。CADPilot 将工具列表压至最小、docstring 保持简短、默认只返回文本，保证长建模会话不耗尽上下文。

**可安全试错。** 建模是不断试错的过程。每次改动都必须可撤销，AI 才能尝试一个方案、回退、再换另一个，而不必从头重建。

**人始终在场。** 用户坐在 FreeCAD 窗口前观察模型的构建过程，应能查看 AI 做了什么、手工修正，并让 AI 基于修正继续。满足这一需求本身发展成一个独立子系统（见第 5 节）。

## 2. 两个进程

```
AI 客户端（Claude Code、Cherry Studio 等）
   |  MCP over stdio
   v
cadpilot MCP 服务器（src/cadpilot，Python >= 3.12，经 uvx 启动）
   |  XML-RPC over TCP，localhost:9875
   v
FreeCAD 插件（addon/CADPilot，运行于 FreeCAD 进程内）
   |
   v
FreeCAD 文档 / GUI
```

MCP 服务器与插件是两个独立进程，通过 XML-RPC 通信，原因有三。

**隔离。** MCP 服务器绝不 import FreeCAD，因此可运行在任何地方，包括另一台机器（用 `--host` 指定）。FreeCAD 重启后，服务器检测到连接失效，重建代理并重试一次。

**生命周期不一致。** AI 客户端可随时启停 stdio 服务器，而 FreeCAD 是长寿命 GUI 程序。插件持有 CAD 状态，不受 MCP 服务器启停的影响。

**库兼容。** 服务器优先从 `mcp.server.fastmcp` 导入 `FastMCP`（MCP 1.x），失败则回退到 `MCPServer`（MCP 2.x）。

XML-RPC 传输超时为 150 秒。socket 超时不重试：操作可能仍在 FreeCAD 端执行，重试意味着它可能被执行两次。

## 3. 单线程约束

FreeCAD 的文档树与 GUI 非线程安全：文档操作必须在主线程执行，而 XML-RPC 服务器运行在自己的线程上。插件因此把每个请求转交主线程；本节其余部分描述转交机制及其边界情况。

每次调用进入任务队列，RPC 线程阻塞等待结果。每次调用拥有独立的应答队列，超时的调用不会误收下一次调用的应答。主线程由 Qt 信号唤醒，另设定时器兜底，防止信号丢失。

插件让位于交互操作：鼠标按键按下或对话框打开期间，队列任务延迟执行，自动化改动不会打断用户正在进行的拖拽。之所以检查鼠标状态，是因为后台启动或远程桌面会话之后，Qt 可能报告一个实际并不存在的按键状态，而程序无法清除该状态，队列将无限等待。其表象是 `ping` 始终应答而所有实际调用超时，与连接中断难以区分。当前该延迟仅在主窗口确实处于活动状态时生效。

队列任务中抛出的异常会被捕获，写入 FreeCAD 的报告视图并作为错误信息返回调用方，处理循环本身不受影响。停止服务器时以哨兵值阻止定时器继续调度，保证干净退出。

`execute_code` 提交的代码运行在插件命名空间的副本中，用户代码里的赋值不会污染服务器自身的变量。

## 4. 工具面设计

### 4.1 一个 `cad()` 工具，而不是三十个

客户端列出工具时，每条工具定义都会注入模型的上下文，无论模型最终是否调用。过宽的工具面在开工之前就已消耗上下文，因此所有改动统一经由 `cad(operation=...)`，操作名作为普通参数传入：

* 对象级：`create_object`、`edit_object`、`delete_object`、`batch`
* Part 特征：`boolean`（可同时多个工具体）、`fillet`、`chamfer`、`loft`、`sweep`、`mirror`、`pattern`、`move`
* Sketcher 与 PartDesign：`variables`、`sketch`、`pad`、`pocket`、`revolution`、`groove`、`thickness`、`draft`、`datum_plane`、`hull`

### 4.2 docstring 预算

docstring 在每场对话中都消耗 token，因此每个 `@mcp.tool()` 的 docstring 只写一至三行摘要加简要参数说明。各操作的完整参考存放于 `tool_docs.py`，模型需要细节时通过 `operation_help` 按需获取。一项测试将 docstring 总量限制在 11000 字符以内，防止该约束在无意中退化。

### 4.3 知识层级

提示词规定了模型的查阅次序：先自身知识，再 `recall_patterns`（已验证建模方案的持久存储），再 `inspect_freecad`（运行时列出对象的属性方法或某模块的 API）。验证有效的方案经 `save_pattern` 或 `session(action="complete")` 写回，供后续会话复用。

## 5. 可撤销性：事务、会话与步骤日志

每个已提交的改动都运行在 FreeCAD 事务内。其上有两套日志，回答不同的问题：**建模会话**位于 MCP 一侧，覆盖整场对话；**步骤日志**位于 FreeCAD 一侧，是用户可见、可驱动的评审循环。

### 5.1 建模会话

会话（`session` 工具，从 `start` 到 `complete`）把每次改动记为一步：操作、参数、结果、操作后文档中的对象清单，以及模型或用户附加的笔记。对象清单即指纹，用于检测文档与日志是否仍然一致。

回滚到第 N 步，就是对每个被移除的步骤执行一次 `doc.undo()` 并截断日志，不删除也不重建模型。被回滚的步骤进入重做缓冲区，直到新步骤到来才清空，与 FreeCAD 自身的重做语义一致。

撤销只有在该步骤确实拥有撤销条目时才有保证，而单纯修改属性不产生撤销条目。没有事务的步骤因此能在回滚中存活——这正是"回滚报告成功、要求丢弃的对象却还在"这一缺陷的由来。现在回滚会先检查撤销栈实际持有的内容，再从三条路径中选择：

* `native`：区间内每一步都拥有事务且成功出栈，无需额外动作。
* `partial`：部分步骤没有撤销条目，按名字删除日志记录的、由这些步骤引入的对象；回复列出步骤号，并说明这些步骤做过的属性修改无法恢复。
* `rebuild`：目标之前的每一步都能从日志重建，此时删除日志建出的对象并重跑第 1..N 步，得到精确复原。

每条回复都会说明走了哪条路径（`native`、`partial` 或 `rebuild`）以及删除了什么。

两个细节保证这三条路径诚实。第一，撤销的结果是被校验的，而不是被假设的。FreeCAD 的撤销栈与 GUI 共享，一条穿插在栈上的手工编辑会顶着回滚的名义被弹出，而弹出的数量仍然对得上，于是"数量正确"也可能把模型留在错误状态。撤销之后，日志会比对对象集合：被回滚步骤创建的对象必须消失，目标步骤应有而日志建出的对象必须在场，任何不符都会升级到重建路径。第二，清理时删除什么由每一步的前后差集决定，绝不做整表快照相减。每张快照都列出整个文档，一旦目标是"日志开始之前"，整表相减就会把日志之前就存在的对象卷进来，删掉用户自己的东西。日志只删除日志建出的对象。

每次已提交的改动还会被审计：一条只读连通性检查在每次 `cad()` 调用后运行，报告脱离整体的零件。审计只警告、不拦截，可全局关闭，超大文档时自动跳过。

会话与模式以 JSON 存储于 `~/.cadpilot/`（或 `$CADPILOT_HOME`），先写临时文件再改名，崩溃不会截断已有数据。

### 5.1.1 让 `execute_code` 可撤销

本节单独说明该机制，因为它决定了代码驱动的建模是否具备可回滚性。

在 FreeCAD 中，直接修改属性不产生撤销条目，撤销条目来自事务。通过 `execute_code` 片段建模的 AI（这很常见，因为它是灵活性最高的工具）产生的改动超出了任何回滚的可达范围，日志中则堆积着阻断一切回滚的步骤。

现在插件把每段代码包进事务，结束后报告该事务是否实际产生了撤销条目。

* 文档发生变化：该次运行记录为普通步骤，恰占一条撤销条目。代码随步骤保存，回滚、重跑与整体重放全部可用；完全由代码建立的模型可以像声明式操作建立的模型一样重放。
* 文档未变化：空提交不产生撤销条目，该次运行记录为只读——不阻断回滚，也不会被重跑。
* 代码抛出异常：事务被中止，失败的运行不会留下部分应用的改动，同一机制顺带消除了这一缺陷。

事务不可嵌套：自行管理事务的片段并入外层包装；包装仅在当前没有未决事务时才开启新事务。

### 5.2 步骤日志与 Steps 面板

会话随 MCP 服务器退出而消失，FreeCAD 侧的用户也看不到它。**步骤日志**是第二套日志，直接存储在文档上（`MCP_StepJournal` 属性），RPC 服务器停止后依然存在。同一套引擎服务两个前端：

* `step_control` 工具，动词包括：`run_next`、`run_all`、`run_to`、`rollback_to`、`reexecute`（先撤销该步，再以合并后的参数重跑）、`accept` 与 `unaccept`、`reject`、`update` 与 `insert`、`replay`（退回起点，从日志重建全部）、`snapshot`、`reset`；
* FreeCAD 内的 **Steps 面板**，包含步骤列表、进度条、可编辑的参数视图与日志控制台。它在 MCP 服务器停止时照常工作，也可以事后打开已保存的文档，重放其构建过程。

以下规则保证该循环的安全性：

* 日志条目写在每步的事务内，但 FreeCAD 的撤销不恢复文档级属性，因此每次回滚与重跑后都要显式对账。`drift` 标志锚定最近一个带事务的步骤，据此检测手动撤销（Ctrl+Z）。
* 回滚只统计带事务的步骤。只读步骤不拥有事务，将其计入会错误弹出更早步骤的事务。
* 只读步骤同样不阻断回滚，因为它可证明未改动任何内容。阻断仅针对"可能改动了文档却没有事务"的步骤，越过它们需要调用方显式传 `force`。
* 已接受的步骤构成软锁：回滚、重跑与 replay 跨越它们都需要 `force=true`。`reject` 是有意的销毁行为，不受此限。
* 同一操作名有两种拼写：batch 的子操作按 RPC schema 原样记为 `action`，日志原生的步骤用 `operation`。日志读取端与首次执行端均接受两种写法，旧插件写下的日志因此得到修复而非拒绝。
* `run_all` 与 `replay` 跳过无法重跑的步骤并如实上报，而非使整次运行失败。每条改动类回复还附带一份紧凑的日志快照，调用方通常无需单独查询状态。

### 5.3 人与 AI 的双向编辑

日志的存在就是为了双方都能编辑。用户在 FreeCAD 的属性面板中修改某个尺寸时，文档观察器会把改动镜像回产出该对象的步骤参数中；重跑该步骤保留用户的值，而非把零件恢复为 AI 最初记录的值。Placement 永远被跟踪，因为重跑会重新应用记录的参数，不跟踪就会把零件移回原点；角度按度数存储，与属性写入端的约定一致。特征类步骤使用固定的属性名映射，但有一条限制：FreeCAD 1.1 中圆角与倒角的尺寸按边存储，只有所有边尺寸一致时才镜像回去。多个步骤触及同一对象时，每个属性归后一步所有。

观察器在引擎亲自驱动文档时必须保持安静。撤销、重做和步骤重跑会触发同样的属性变更通知，但它们写入的是被恢复的旧值或参数里已有的值。把这些当成人手工编辑，正是重跑悄悄撤销用户几分钟前修正的成因：撤销恢复了旧值，观察器把这次恢复当成编辑镜像回日志，重跑就按旧值重建了零件。引擎驱动的窗口现在会让观察器静音；用户在属性面板里的真实编辑不会发生在这些窗口之内。

`snapshot` 动词覆盖另一方向：用户完全在日志之外完成的工作。它追加一条"已完成、已接受、但不可重跑"的标记，防止手工成果被静默回滚；其前后对象清单明确指出日志遗漏了什么。待执行的计划在快照后保留，因为快照是标记，不是改动。常见流程只需一次调用：先审阅确认前面的好步骤，再到 GUI 里手工完成复杂的部分，然后带上 `accept_done` 保存快照（它会把所有已完成步骤一并标记为接受），AI 从这里继续。回滚到快照会保留手工成果；跨过快照回滚则与任何已接受步骤一样，需要显式的 `force`。

## 6. 草图与参数化特征

草图在单个事务内原子构建：几何体（其列表顺序即约束引用的 GeoId）与约束一并提交并立即求解。回复报告自由度、是否全约束以及求解器警告。规格冲突或畸形时回滚，并返回求解器的诊断（例如哪些约束冲突）。

补充细节：

* `external` 外部几何只能引用其他对象的边与顶点的起点和终点——引用中点在求解时必然失败，该情况在提交前即被拒绝并给出明确提示。位于草图本体之外的引用目标通过 `PartDesign::SubShapeBinder` 自动桥接，因为 PartDesign 不接受本体之外的外部几何。
* 基准面可依附于原点平面或已有面，草图可依附于基准面。
* **按方向依附草图，而非按面名。** `plane={"face": [obj, "+Z"]}`（亦支持 `-Z`、`+X`、`-X`、`+Y`、`-Y`，以及 top、bottom、left、right、front、back 等别名）选取法向指向该方向的平面，多面同向时取最外侧者。FreeCAD 每次添加特征都会重新推导面名，上一个特征上的 `Face5` 到下一个特征可能指向别的面；按名字依附可能把草图贴到侧壁上，pocket 未切除任何材料，调用却仍报告成功。作为兜底，pocket 或 groove 未切除任何材料时会返回警告。
* **阵列复制的是特征，不是实体。** 对 PartDesign 特征，`pattern` 在同一 Body 内创建以该特征为原始项的 `PartDesign::PolarPattern` 或 `LinearPattern`，把孔或肋复制到整个零件上。对 Part 级对象（布尔结果、基础体），则用 Draft 阵列复制对象本身。实测 FreeCAD 1.1 的 PartDesign 阵列无法经 Python 可靠驱动，因此当变换无可见效果时操作会明确报错，而不是在请求六个孔时只返回一个孔的结果。
* **依附融合。** 草图依附在实体表面上时，对它做 pad 或 pocket 直接作用于该实体：pocket 切除，pad 融合。此时先 pad 再布尔减是错误做法。
* `hull` 将两至三张视图轮廓草图沿各自法向拉伸后求交，得到可视外壳。结果为普通 `Part::Feature`，重载文档后依然存在；同名重跑就地替换形状，便于迭代。
* 以 `=` 开头的字符串形式的属性值经 ExpressionEngine 绑定而非直接赋值，电子表格驱动的全链参数化正是基于这一机制。

## 7. 几何查询

`measure_geometry`、`get_topology`、`check_interference`、`get_positioning_info` 是只读的形状查询，派发到 GUI 线程且不开事务。

坐标一律为全局坐标：形状的存储几何已包含其 Placement，因此不做手工变换（早期版本的双重变换 bug 使这条规则得以确立）。拓扑列表按尺寸排序并分页，每张面、每条边都带有类型、中心、法向及半径或轴等信息——模型据此为圆角选边、为草图选面。数字仅在报告出口处舍入到四位有效数字；定位零件的计算全程使用全精度。

## 8. 零件定位：锚点与装配

零件之间的相对定位是 AI 驱动 CAD 中最难的问题。CADPilot 以数据而非截图解决它。

**锚点**为对象上的点和方向命名。一部分自动推导（包围盒的中心与各角、质心、主导圆柱面的轴线、最大平面面的中心），模型与用户也可自定义。自定义锚点以局部坐标存储在对象上，零件移动时随之移动。

**`assemble`** 接受一列配合，每条指定对象、锚点、目标与目标锚点，外加模式（`center`、`touch`、`axis`）与可选偏移。全部配合在单个事务中一次应用，随后每个锚点在新位置重新解析，逐条报告残余距离与角度。任一配合超差即整体中止。

**`align_shapes`** 是单元素版本：将对象的一个面、边或顶点与目标元素对齐。

**`verify_assembly`** 审计整个文档：不与任何零件接触的悬空件、空间重叠对、按容差校验的具名锚点对，以及一张由已扫描对构建的接触图——它把相互接触的零件归组，报告脱离主装配的孤岛。

### 8.1 带持久关节的装配会话

`assembly_session` 是独立的状态机，构建于 FreeCAD 1.1 原生 Assembly 工作台之上：先固定基准件，再添加组件、建立配合、求解、验证、完成。组件是持有 Placement 的 `App::Link`，关节持久保存在文档中，移动父件后重新求解，子件随之移动。

以下规则保证其可靠性，均在真实 FreeCAD 上验证过：

* 求解器的准备步（matchJCS）必须在最终那次 `solve(True)` 之前运行；重复求解会破坏求解器保存的状态。
* 组件形状为全局坐标，关节引用却是零件局部坐标，因此残差以几何方式测量（面间距、法向夹角），绝不经过关节坐标系自身的数学。
* 配合可指定面、锚点或点；指定面时由最近的顶点决定落点，与 GUI 点击选择的行为一致。
* `trim={"winner": ...}` 执行声明式优先级裁剪：在败方局部坐标系中烘焙一次非破坏性切割，再把 link 重新指向结果。每步都预计算自身的撤销负载，回滚即一条合并后原子执行的请求。
* MCP 侧先校验插件的返回结果再记录任何状态，失败的请求不会留下改到一半的会话。

## 9. 截图策略

截图只来自一个工具：`get_view`，其余工具一律纯文本，token 占用保持稳定。每张截图写入 `$CADPILOT_HOME/screenshots/`（保留最新 100 张），响应只带文件路径文本，图像数据不进入上下文；多模态客户端用自己的文件读取工具打开 PNG。`--only-text-feedback` 连 `get_view` 也只回文本提示，为纯文本模型提供硬保证。长边默认不超过 384 像素，除非显式给出尺寸。少数视图类型（如 TechDraw、Spreadsheet）无法截图，返回空。

## 10. 长时间计算

`execute_code_async` 在后台线程中运行代码并返回任务 id。状态、打印输出与异常栈保存在一个有上限的内存注册表中（最多 50 个任务），通过 `get_task_result` 轮询。后台代码通过 `task_print` 或 `FreeCAD.Console` 汇报，而非 `print`，因为从线程重定向进程级 `sys.stdout` 会与其余使用方发生竞态。后台代码不得触碰文档与 GUI——那是同步 `execute_code` 的职责。

## 11. 信任与边界

RPC 服务器默认仅监听 localhost。远程访问需显式开启，开启后绑定到所有网卡，并由一个过滤服务器强制执行 IP 或网段白名单；非法条目在配置阶段即被拒绝。

`execute_code` 在设计上就是任意代码执行。它作为逃生舱保证了第 1 节承诺的完整控制力，也正因如此，威胁模型把任何能连上服务器的客户端都视为完全可信。这一取舍是有意的：远程访问默认关闭，开启后还须经过白名单。`--host` 的值在启动时校验。

## 12. 故障处理

* **重连。** 连接失效时客户端重建代理并重试一次，覆盖 FreeCAD 或插件重启的场景。
* **前后兼容。** 新客户端对旧插件自动降级，旧客户端对新插件照常可用。
* **名称规范化。** FreeCAD 会改写对象名（空格变下划线、重名加序号），因此所有处理器都返回 FreeCAD 实际选定的名字。
* **版本差异靠探测。** 同一设置在不同版本中存储布局不同时，插件在运行时探测该用哪种。
* **热重载。** 开发期间插件无需重启 FreeCAD 即可重载；停服与重启之间的罕见竞态也有成文的修复路径。
* **FreeCAD 不可用时的诊断。** `diagnose` 工具完全运行在 MCP 一侧、绝不 import FreeCAD，因此 FreeCAD 未运行或卡死时仍能工作。它报告 RPC 端点、FreeCAD 进程、各用户目录下的插件安装情况以及插件的启动日志，最后给出具体建议。它最有用的判定是：端口在监听但 ping 不应答，意味着 GUI 线程卡死，而非配置错误。
* **GUI 卡死时插件日志仍可读**，因为其处理路径刻意绕开 GUI 线程。日志为一个小型环形缓冲加一份磁盘文件，每条记录都标注了引发它的请求。
* **启动引导陷阱。** FreeCAD 以 `exec()` 运行插件的 `InitGui.py`，导致该文件中定义的函数无法引用文件顶层导入的名字。因此启动代码所需的每个名字都在启动函数内部导入。此处的崩溃会写入一个日志文件，`diagnose` 知道其位置。

## 13. 测试

pytest 套件（约 325 个测试）以一个记录每次调用的假 XML-RPC 连接覆盖 MCP 服务器侧：响应整形、截图策略、重连行为、会话与模式状态机、`cad()` 派发、装配状态机（含失败路径）、下一步建议启发式以及 docstring 预算。

插件离开 FreeCAD 便无法 import，因此第二层测试用 Python 的 `ast` 模块解析插件源码，钉住那些只在运行时才会静默失效的契约：`InitGui.py` 的命名空间规则、Steps 面板的信号接线、batch 子操作名的两种拼写，以及 replay 的跳过行为。诊断套件覆盖各平台的路径布局、真实的本地端点、关闭的端口，以及工具可能给出的每种判定。

需要真实 FreeCAD 的部分由 `tests/live_sketch_verify.py` 做端到端验证：构建一个参数化支架，检查电子表格数值是否传播、失败时报告什么，以及撤销是否干净。
